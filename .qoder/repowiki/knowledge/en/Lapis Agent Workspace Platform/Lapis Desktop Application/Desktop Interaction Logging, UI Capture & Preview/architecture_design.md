Two loosely coupled subsystems coexist under `lapis::desktop`:

- Interaction logging (`interaction_log.{hpp,cpp}`, `interaction_recorder.{hpp,cpp}`): `InteractionRecorder` is a GUI-thread `QObject` that installs a Qt event filter on the workspace's windows and translates key/IME/mouse/wheel/window events into structured `QJsonObject` records. It exposes a `namespace interaction` API (key_outcome, paste, wheel_outcome, copy, cause) so other modules report what they did with input; in previews/test fixtures those hooks are no-ops. Records are handed to `InteractionWriter`, which runs in its own `std::thread`, serializes JSON lines to `<data>/runtime/interaction.jsonl`, rotates files by size/count, drops overflows, and flushes via condition variables. `PointerSampler` folds rapid pointer moves into one sample per interval, and `likely_secret_prompt` + `key_class` redact keystrokes typed while the cursor sits on a likely secret prompt.
- UI capture & preview (`ui_capture.{hpp,cpp}`, `ui_preview.{hpp,cpp}`): `UiPreview` is a `QObject` host that owns a `QQmlApplicationEngine`, loads a QML source URL into an isolated `QQuickWindow`, and exposes C++ objects (`alerts`, `agentSearch`, `usage`, `tools`, `desktop`, `conversations`, `terminals`, `limitResets`, `nextPrompt`, `planSignIn`, `guiState`) through `QQmlContext`. `capture_window` drives a scripted capture flow against that preview using `CaptureOptions` (image path, trace path, scenario, delay, smoke_input).

Dependency direction: recorder depends on the writer and the settings model; capture depends on both preview and workspace but not on the recorder; preview depends only on workspace/keymap/QML infrastructure. The two subsystems do not depend on each other.
